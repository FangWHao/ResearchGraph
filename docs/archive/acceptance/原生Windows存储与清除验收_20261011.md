# 原生 Windows 存储与整项目清除验收

## 环境与范围

实际 Windows 进程运行 Python 3.12.3，`os.name=nt`、`sys.platform=win32`，系统默认编码 CP936，`utf8_mode=0`。公开 uv 0.12.24 的 Windows 下载摘要与官方发布资产一致，依赖和 Python 仅放在忽略的项目缓存，不改全局 PATH、注册表、个人客户端设置或日常钩子。测试材料全部为公开合成资料。

本轮核验对象写入、中文 schema、数据目录共享／独占系统锁、SQLite backup API、管理目录整项目清除、强杀后恢复和重导入屏障。开发开始前另存并验证可恢复的原提交 bundle。

## 实际故障与修复

旧安装包在默认 CP936 下创建数据库发生 `UnicodeDecodeError`；原子正文已改名发布后，又因不存在 `os.O_DIRECTORY` 报错。这两个故障用仓库外 `-I` 实际安装复现，未通过切换全局 UTF-8 模式隐藏。

- schema 明确读取 UTF-8。Windows 原件在同目录临时文件中写完、flush／fsync 后，经宽字符 `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` 发布；失败保留已有目标并清理本次临时文件。Linux 保留文件及目录 fsync。
- Windows junction 不是 `is_symlink()`。管理子路径逐级 lstat，拒绝符号链接和 Windows 重解析点；覆盖预览、回执读取、恢复删除路径及重导入屏障。数据目录本身的既有别名仍共享同一系统锁；不是任意祖先链接都被当成新的管理归属。
- Windows 钩子错误日志采用宽字符原生句柄只追加，打开时不跟随重解析点，固定目录句柄、拒绝目录替换；日志只记时间、阶段与异常类型，不保留被拒绝的输入。钩子保持静默 exit 0。
- 原有测试现在在 Windows 使用真实 NTFS junction，在 Linux 使用目录符号链接。删除测试链接本身时不递归删除外部目标。公开测试回执按 UTF-8 读取；CLI 子进程只显式设置控制台编码，默认文件编码不变。

接口依据：[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)、[FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)、[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)。调用标志及实际进程验收不证明断电后的全部目录元数据持久性。

## 边界与下一步

本轮没有执行真实项目清除、读取完整原会话或发送远程模型请求。未模拟断电，不改动卷缓存或请求管理员权限；Windows 清除删除后的目录同步没有与 POSIX fsync 等同的证明。未完成大规模清除、完整 Windows 影子快照、物理文件摘要与本地 ZIP 导出；其中仍有 POSIX 描述符调用，后续按实际缺口继续移植与验收。

用户授权自主开发后，普通实现选择由 Agent 记录并推进；不能将这批合成结果记作 试点项目 正式人工参考、真实模型质量、全部 M2 采集或 M3 两周使用。整体 M0–M4 保持未完成。
